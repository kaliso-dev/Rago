# Proxy

Linear RAG-50 : nouveau produit, d'abord en Europe, à intégrer à l'app. Consigne du 17/10 : « à moindre coût voir gratuitement », sinon mis de côté.

- **Données en prod depuis le 29/10** : chaque [[Test réseau]] envoie ville, fournisseur, ping, gigue et pertes vers Hypixel, Minemen EU, Cloudflare et 6 villes candidates (Paris, Francfort, Londres, Stockholm, Madrid, Virginie). Admin : `/admin/reseau` ([[Serveur de licences]], `network.js`, `geo.js`).
- **Ce qui manque** (analyse du 29/10) : 1) le trajet proxy → serveur de jeu, mesuré depuis chaque ville (le plus important, sans toucher à l'app) ; 2) tester les vraies adresses de l'hébergeur choisi (les villes sont mesurées sur Amazon) ; 3) traceroute (nouvelle version d'app) ; 4) Wi-Fi ou câble (nouvelle version) ; 5) volume de mesures.
- Hypixel passe par Cloudflare : un proxy n'aide que si le trajet du fournisseur jusqu'à Cloudflare est mauvais.
- À ne pas confondre avec le [[Packet Optimizer]], qui ne change pas la route.
- **Relancé par Sofiene le 04/11** (« maintenant je veux qu'on développe les proxy ») : après le test réseau, l'app analyse la meilleure route vers Hypixel (et les autres serveurs Minecraft) et propose le meilleur proxy. Fil « Développer les proxys Minecraft ».

- **Page du site** : `route.html` présente Rago Route aux joueurs (en test, bouton Discord, aucun prix) ; voir [[Site]]. Pas encore en ligne (07/11).
- **Prototype Rago Route écrit le 06/11** (Sofiene : « développons ça ce soir ») : `proxy/rago-route.py`, Python sans dépendance. Mode `client` (PC/Mac : ports locaux 25565 → Hypixel, 25566 → Minemen ; `--sortie IP`, `--via IP` pour un trajet par un relais Rago, `--interface enX` pour la 4G, `--perte-test` pour simuler des pertes) et mode `sortie` (serveurs, UDP 25600 ; sert aussi de relais). Protocole maison sur UDP : paquets numérotés envoyés par tous les trajets, confirmations, débit limité, session gardée 60 s sans nouvelles du joueur ; nom du serveur réécrit dans le handshake. Testé contre Hypixel depuis le Mac de Sofiene (06/11) ; **jamais testé sur Windows**. Pas encore : réparation par paquets de secours (FEC), jeton d'accès, chiffrement du tunnel.
- **Version du 07/11** (après le log de partie du 07/11, voir plus bas) :
  - un paquet est renvoyé dès qu'un paquet parti après lui est arrivé (l'horodatage renvoyé dans chaque confirmation dit lequel), avec une marge d'un quart d'aller-retour ;
  - si plus rien ne revient, seuls les 2 plus anciens paquets sont renvoyés pour sonder, et le délai repart à chaque confirmation (comme TCP) ; dès que le réseau revient (réponse au ping ou paquet du joueur), les plus anciens repartent tout de suite ;
  - l'aller-retour n'est mesuré que sur la première confirmation de chaque paquet ;
  - toutes les confirmations en attente sont lues d'un coup, et après un blocage du programme (plus de 20 ms de retard) on attend un tour avant de déclarer des pertes ;
  - sur Mac, le programme demande au système de ne pas le ralentir en arrière-plan (App Nap ; option `--sans-anti-veille` pour l'éviter) ; essayé le 07/11 : l'appel marche, mais le programme se réveille encore 6 à 78 ms en retard (souvent 11 à 40), donc la mise en veille n'est pas (seule) en cause ;
  - l'affichage donne aussi le retard du programme et les renvois de la sortie, et pour chaque trajet la part des paquets arrivés en premier et les Mo reçus (pour juger un trajet 4G et sa consommation).
  - Tests locaux du 07/11 (réseau simulé à 24 ms, trafic de jeu, comparaison avec la version du 06/11) : programme gelé 60 ms toutes les 0,7 s → renvois inutiles du joueur 138 → 0 ; sans perte → 99e centile 54 → 35 ms, renvois 54 → 0 ; 20 % de pertes sur les deux trajets → 99e centile ~170 → ~130 ms ; coupure totale de 8 s → reprise en 10 à 20 ms au lieu d'environ 1 s ; 20 Mo sans erreur avec 20 % de pertes sur les deux trajets.

- **Autres jeux (réponse du 05/11)** : Minecraft Java d'abord (TCP, un serveur choisi par le joueur, relais local sans pilote). Les jeux UDP (Valorant, CS2, Fortnite, Apex) demandent un pilote réseau Windows qui capte le trafic du jeu (comme ExitLag), des serveurs près de leurs centres de données et l'accord de chaque anti-triche (Vanguard, FACEIT, EAC : À VÉRIFIER) ; gain de route faible sur Valorant/LoL (Riot Direct) et CS2 (relais Valve). Conseil : Minecraft d'abord, extension ensuite.
- Détail de l'idée de départ : « double trajet anti-lag » : l'app envoie chaque paquet par la route directe et par un proxy, la sortie garde le premier arrivé ; ne baisse pas le ping moyen mais supprime les pics dus aux pertes (comme ExitLag ou Mudfish).
- Installation : `scp install.sh root@IP:`, `ssh root@IP`, `sh install.sh` (utilisateur `root` chez Vultr).
- **Logiciel** : `proxy/` du dépôt (copie dans le dossier du projet, `proxy/`) : `relay.py` (relais TCP Python sans dépendance ; port 25565 → `mc.hypixel.net`, 25566 → `eu.minemen.club` ; réécrit le nom du serveur dans le handshake ; TCP_NODELAY ; 8 connexions max par IP ; journal sans IP), `mcping.py` (ping Minecraft), `rago-route.py` (tunnel Rago Route, voir plus haut), `install.sh` (généré par `fabriquer-install.py` : services systemd `rago-proxy` et `rago-route`, BBR, tampons UDP jusqu'à 4 Mo, pare-feu ufw SSH + 25565/tcp + 25566/tcp + 25600/udp, ping vers Hypixel et Minemen à la fin). Installé sur de vrais serveurs Vultr et utilisé contre Hypixel depuis le 05/11 (CONFIRMÉ).
